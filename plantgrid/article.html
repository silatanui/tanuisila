PlantGrid

A portfolio demo of an ICT operations console for plant work: cases, assets, maps, messages, and the modules around them

Open the live dashboard

Public overview: plantgrid.tanuisila.dev · Accounts: sign in

PlantGrid is a working demo of how I think an ICT desk for a manufacturing site should feel. Not a gallery of empty charts. A console where open tickets, asset records, plant locations, and short messages sit close enough that you can move between them without losing the thread. The plant is made up. The modules are real in the browser. Screenshots in this post come from the live app at plantgrid.tanuisila.dev.

The sample site is called Northridge Processing: packaging and processing halls, a server room, office blocks, and the usual ICT kit — printers, PCs, switches, access points, file servers. Sign-in offers several roles (admin, ICT manager, technician, department manager, employee, auditor) so the same console can show different permissions. Monitoring samples and backup runs are labelled as simulated. The demo does not talk to real plant equipment.

Why I built it

A lot of portfolio “ops” demos look finished until you try to do ordinary work in them. You get a ticket list in one place, an inventory table somewhere else, and no clear way to go from “this printer is down” to “here is the record, the hall, the owner, and the last note.” On a real plant that chain matters. Someone raises a case. Someone owns it. Someone goes to the floor. Someone updates the asset so the next person is not starting from zero.

PlantGrid puts those pieces in one product. From an open case you should reach the asset, the location on the map, related network or server context if you need it, and a place to leave a status note. That is the main design bet. The rest of the UI is there to support that path, not to decorate it.

In practice I cared about a few concrete rules:

  1. The dashboard should show load and overdue work first.
  2. Case status should follow a visible path: New → Assigned → In Progress → Pending → Resolved → Closed.
  3. Asset pages should hold useful fields (photo, specs, location, linked tickets), not only a name and a serial.
  4. Location codes on records should match something you can find on a plant map.
  5. Different roles should see different menus and actions.
  6. Any assistant help should read the same demo data the screens use, and wait before changing anything.

Dashboard

After login, the dashboard is the default landing page. It opens with a short greeting for the signed-in user, the date, and two common actions: open cases or create a case. Below that are summary cards for assets, maintenance load, open tickets, and critical incidents. There is also a warning strip that says critical readings are simulated. I kept that strip visible on purpose. If a demo pretends those numbers come from live plant sensors, it teaches the wrong lesson.

Further down you get upcoming work and a recent-cases list. Overdue items stay easy to see. The side panel shows open-queue counts, a short checklist for moving work, and shortcuts into assets, the map, and monitoring. The top bar has global search plus badges for alerts and messages. Together that is enough to start a shift without hunting through menus first.

"Show overdue work before you show charts that only look busy."

Cases

Cases are the main unit of work. From the console you can use the full queue or a narrower “my open cases” view for tickets you requested, own, or partner on. Columns cover case number, subject, requester, priority, status, SLA state, and owner. Breached SLAs are easy to spot. Filters stay simple: search by number or subject, limit by status or priority. The table is meant for scanning under time pressure, not for building long reports.

A case detail page shows the lifecycle stepper, request fields, due times, and a notes/activity column. Many records also link to an asset. One seeded example is a high-priority security ticket about suspicious login alerts; another common walkthrough is a packaging printer fault. The point is the same either way: the ticket should not float free of the device and place it affects. Partners can be added or ownership transferred. History stays on the case so the next person can read what already happened.

Status updates are where handoffs happen. You can change owner, leave a note, optionally log completed maintenance against the asset, and mark the asset active again in one pass. Notes support @mentions and links to other case IDs when work spans more than one ticket.

Assets

The asset register holds devices with enough detail to be useful on the floor. A typical record includes a photo, form factor, connectivity, location, and assignment to a person or department pool. Linked cases appear under the record so you can see past and current work. Note fields can be cleaned up with refine/paraphrase helpers before save; those helpers edit wording, they do not invent new facts about the machine.

Network, servers, and production follow the same idea: hostnames, IPs, roles, and locations stay next to the cases that mention them. You should not need a separate spreadsheet to learn which switch sits in packaging or which host runs the file share.

Plant map

Location tags on tickets and assets only help if they map to space. The Northridge campus plan shows the main halls and rooms with pins you can zoom, pan, and click. When a case says Packaging Hall, you can find that hall on the map and relate it to the asset and open work. It is a navigation aid for people who still have to walk, not a decorative floorplan for the marketing page.

"A ticket ID without a place is hard to act on. A map without open work is just a tour."

Messages and assistant

Not every coordination note belongs on a formal ticket. The messages inbox holds short direct messages between demo users — parts requests, archive warnings, shift handoffs. Unread and delete stay on the row. It is a small inbox on purpose. I did not want a second chat product competing with the case queue.

The in-console assistant answers from the same Northridge sample data. You can ask about open case counts, assets, or docs. Prompt helpers on notes (refine, paraphrase, shorten, clarify) sit above the composer. Actions wait for confirmation. That rule is boring and I kept it anyway: in ops software, auto-acting without a check is a good way to make a second mess while cleaning the first.

Docs and performance

Documentation is a searchable list of short guides: getting started, picking a demo role, finding menus, raising an issue, following cases, using messages, searching people and assets. The audience column marks most of them for first-time users. If someone needs a private walkthrough call just to click around, the demo still has work to do.

Performance is the manager view: team throughput, SLA hit rate, unassigned open work, and overload flags. Charts compare open vs resolved by person and show ticket mix by status or priority. An overload warning names who is carrying too many open items so throughput numbers are not read in isolation.

Security, backups, reports

Beyond break/fix tickets, the demo includes security review screens, labelled backup runs, and reports. They exist so a walkthrough can cover control and summary work without claiming live plant integrations. Simulated items stay labelled.

Appearance

Theme colour and page background can be changed per browser. Tables and cards stay light enough to read. Dark mode is available; it is not forced as the product default. Sign-out is at the bottom of the profile menu.

A short walkthrough

If you have about ten minutes:

  1. Sign in with the System Administrator demo account (or another role if you want a narrower console). Password is on the login page.
  2. Skim the dashboard for overdue work and open critical items.
  3. Open any high-priority case. Follow the status path and any linked asset.
  4. Check that asset in Assets, then find its hall on the plant map.
  5. Look at Messages, ask the assistant a factual question, and optionally open Performance or Monitoring.
  6. If you stall, use Documentation.

What it is not

PlantGrid is not a commercial CRM and not a control system for real machinery. Monitoring and backups in the demo are simulated. People and tickets are sample data. I left live plant control out because the goal here is product and interface craft for ICT operations work, not a fake factory remote. Inside the signed-in app I also avoided a loud marketing homepage. The public landing page introduces the project; the dashboard is for doing the work.
